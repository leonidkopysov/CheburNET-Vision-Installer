# Аудит ЧебурNET Vision Installer по техническому заданию

Дата: 11 сентября 2026 года. Основание: `TZ_AI_Audit_Bash_Script_CheburNET.pdf`, 15 страниц.

Проверена исходная ветка `main`, коммит `219a52620bfde13f7fd06ec7f8f9831867f69e8e`, а не релизный архив. Исправления подготовлены в ветке `audit/tz-20260911`. Номер приложения 1.1.3 сохранён; изменение релиза и тега не входит в эту работу. Встроенные Auto Tuning и Traffic Control после исправлений — локальные аудированные варианты снимков 1.0.0, а не неизменённые upstream-файлы.

**Результат:** подтверждённые ниже дефекты исправлены; выполнены ручной разбор, второй отдельный проход, безопасные регрессионные тесты и проверка сборки. **Production-приёмка не завершена:** настоящая установка, перезагрузка, сетевые проверки на Ubuntu/Debian и ARM-сервере в этом прогоне не выполнялись. Успех модульных тестов не заменяет эти испытания.

## 1. Объём и порядок работы

Прочитаны основной Bash-установщик, вспомогательные shell/Python-файлы, встроенный Auto Tuning, Traffic Control, systemd-юниты, генератор профиля/Compose/nginx, сборщик, тесты и CI. Проверены роль сайта-заглушки, пути, передача настроек, права, внешние источники и восстановление. Бинарные изображения оформления не являются исполняемыми компонентами аудита.

Сначала составлена карта исполнения и сообщены находки по критичности; затем внесены исправления. После них выполнен второй отдельный проход по изменениям и вызовам функций. Это самопроверка, не заключение второго независимого специалиста.

Безопасные тесты подменяют команды, которые могли бы менять сервер. На машине аудита не запускались установка, UFW/nftables-применение, настройка SSH, systemctl enable/restart, APT upgrade или реальный Certbot.

## 2. Карта архитектуры

### Последовательность

Подтверждение → проверка ОС/root/systemd → APT с согласованием → проверка введённых данных/DNS/конфликтов → Docker → атомарная публикация проекта → nginx/bootstrap → pull и закрепление образа → Auto Tuning и ограничение API → SSH/TFO/ICMP → запуск ноды → сертификат и пробное продление → опциональный Traffic Control → проверка в дочернем процессе → фактический отчёт → профиль для панели.

API запускается после защиты. Назначение профиля Remnawave остаётся внешним шагом: до него код `2` означает ожидание TLS/443, а не успешную сквозную работу клиента.

Глобальное состояние установщика: фиксированные `BASE`, `CHEBURNET_VERSION`; временные `WORK`, `STAGING`; флаги `APT_APPROVED`, `ACME_OPEN`; палитра. Режимы: установка, продолжение, проверка, вывод, preview, render, версия/справка. Внутренний `--check-internal` сохраняет `errexit` без повторного захвата родительского flock.

Глобальное состояние тюнинга: пути `CONF`, `SNAPSHOT_DIR`, `BACKUP_DIR`; найденные `*_BIN`; вычисленные CPU/RAM/сетевые цели; `DESIRED`/`MANAGED_KEYS`; счётчики изменений/конфликтов; статусы ZRAM/RPS/служб; `CHEBURNET_*`-переключатели. Вызов из Vision отключает отдельную автоматизацию сертификатов и key-only SSH: этими этапами управляет Vision. Наличие таких standalone-веток не означает двойной запуск.

Глобальное состояние Traffic Control: `ROOT`, `STATE`, `BIN`, `SHORT_BIN`, `SYSTEMD`, `UNIT`, `TABLE`, `SOURCES`, ограничения загрузок/записей. В state — SSH-порты, исключения, ручные блокировки, три списка и время; отдельные маркеры enabled/pending. Операции сериализованы flock; RDAP не держит блокировку активации.

## 4. Старые хвосты, которые нельзя удалять вслепую

Сохранены миграция собственных старых sysctl-файлов, отключение прежнего cheburnet-conntrack.service, обработка прежних глобальных лимитов, удаление только собственных ACME-правил, восстановление из `.bootstrap-pending`, legacy-команда TC `confirm`. Они обслуживают установки предыдущих редакций и не являются доказанным мёртвым кодом.

Сохранены самостоятельные режимы сертификатов/SSH в снимке Auto Tuning: Vision их отключает флагами, но удаление изменило бы standalone-поведение компонента. Не удалены чужие конфиги, units, cron, firewall или контейнеры «по похожему имени».

Длинный APT-вывод из пользовательского лога сам по себе не доказывает дублирование установки. Там отдельные транзакции Docker и nginx, каждая запускает package triggers/needrestart. Дополнительно есть simulation плана, которая ничего не устанавливает, и реальная операция. Повторный ACME dry-run проверяет продление, а не повторно выдаёт production-сертификат. Новая завершённая установка не повторяет эти этапы через `--resume`.

## 6. Совместимость и границы безопасности

Фильтр ОС проверен тестом для Ubuntu 22.04/24.04, Debian 12 и ранее разрешённого Debian 13; архитектуры x86_64/aarch64, неподдерживаемая i686 отклоняется. Это **проверка фильтра**, не подтверждение запуска всех зависимостей. Новая платформа не добавлялась. Требуются systemd и поддержка необходимых возможностей ядра/AppArmor/nftables. Возможности ARM-образа и конкретного ядра должны быть проверены на целевой машине.

Не добавлены `eval` пользовательского ввода, `curl | bash` для стороннего компонента, отключение TLS-проверок, глобальный `flush ruleset`, сброс UFW или удаление каталогов ОС. Встроенный архив проверяется SHA-256 до распаковки; это контроль целостности, не независимая подпись автора. Docker Signed-By ограничивает источник ключа, но заранее доверенный fingerprint и заранее закреплённый digest образа не добавлялись.

Сохраняющиеся эксплуатационные ограничения:

- Нет полного транзакционного отката APT, Docker, sysctl, UFW и всех служб после ошибки. Нужны снимок VPS и аварийная консоль.
- Правило SSH allow и сохранение аутентификации не доказывают отсутствие блокировки в firewall провайдера, других nftables chains, UFW deny выше по порядку либо SSH Match. Автоматически переписывать такие конфигурации без инвентаризации нельзя.
- ACME-аренда ограничивает сохранение временного исключения при обновлении TC, но сама не удаляет уже загруженное правило по таймеру. После SIGKILL проверять TCP/80 вручную; есть post-hook и загрузочный cleanup. Глобальные Certbot hooks рассчитаны на выделенную машину, не на произвольную многосервисную конфигурацию.
- `live_rules_match` намеренно не признаёт неизвестную структуру JSON успешной. На иной версии nft возможен безопасный диагностический отказ; нужна проверка реальных JSON Ubuntu/Debian до production.
- Действующий `fq` корневого интерфейса не подменяется вслепую: отчёт отдельно называет `qdisc по умолчанию`. NTP/TRIM/ZRAM могут давать предупреждение из-за ограничений VPS.
- Старый уже установленный менеджер не обновляется публикацией на GitHub. Новый файл — полный комплект для новой установки. `--resume` не является мигратором; для старой ревизии использовать её сохранённый менеджер, не заменять один helper вручную.

Семантика nftables сверялась с [официальным руководством Netfilter](https://netfilter.org/projects/nftables/manpage.html): JSON-вывод, check-режим и флаг dormant. Предложенные регрессии не подменяют проверку в реальном ядре.

## 7. Повторная проверка и сборка

- Модульные/regression-тесты: 80 тестов. Новые проверки входят в `tests/test_audit_tz.py`; прежние 65 тестов сохранены и адаптированы к новому интерфейсу/timeout-обёрткам.
- ShellCheck 0.11.0, уровень style: все shell-источники, встроенный Auto Tuning и полный установщик. Точечные SC2016 объясняют намеренно отложенные подстановки; SC2317/SC2329 — функции trap. Проверки не выключены целиком.
- `bash -n`: shell-исходники, vendor и собранный файл. Python-модули проверяются компиляцией и тестами.
- Сборка воспроизводима; SHA-256 файла и встроенного архива сверяются. В payload входят оба новых модуля отчёта/UI и обновлённые вспомогательные файлы.
- CI расширен на весь shell-код, включая Auto Tuning; релизный workflow и существующий тег не изменялись.

Команды воспроизведения:

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 build.py
for file in src/*.sh vendor/cheburnet-auto-tuning.sh cheburnet-vision-install.sh; do bash -n "$file"; done
shellcheck -S style src/*.sh vendor/cheburnet-auto-tuning.sh cheburnet-vision-install.sh
sha256sum -c SHA256SUMS
```

Второй проход дополнительно проверил ссылки на удалённую report_row, включение новых модулей в payload/публикацию, код 2 при ожидании профиля, отсутствие вложенного flock менеджера, stdout/секреты, порядок SSH-отката и ошибку несовместимого сохранённого комплекта. Запуск настоящих Xray/nginx-интеграционных тестов этого изменения не заявляется: соответствующие бинарники/серверный стенд в прогоне отсутствуют.

## 8. Обязательная приёмка перед production

На отдельных VPS с консолью провайдера: Ubuntu 22.04, Ubuntu 24.04, Debian 12; отдельно arm64, если нужна эта архитектура. Для каждой ОС выполнить чистую установку, вход второй SSH-сессией, назначение профиля в Remnawave, VLESS-клиент извне, `--check`, `ctc check`, ACME dry-run при активном TC, повторный `--resume`, перезагрузку и повтор проверок. Сверить nft JSON, порядок UFW, фактические soft/hard NOFILE и ZRAM. Обрывы/SIGKILL проверять только на расходуемом стенде.

После этих испытаний можно подписать production-приёмку. До них результат — исправленный и локально проверенный кандидат, а не гарантия безошибочной работы на любом сервере.
